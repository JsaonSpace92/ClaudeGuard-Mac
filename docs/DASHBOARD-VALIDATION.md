## UDP 分层诊断新增与真实链路结果

2026-10-07：用户要求继续使 UDP 功能可用。新增 `src/socks_udp.rs`，按 RFC 1928 使用保存的本机 Mixed/SOCKS 入口申请 UDP ASSOCIATE；保持 TCP 控制连接，最多三次 STUN 探测，严格校验封装、事务标识和有效 STUN 出口。中继只能是本机回环地址，不回退到外部中继或其他节点。

实际只读状态：TUN 开启、本机 Mixed 端口支持 SOCKS5、本机 UDP 协商成功、运行时 SOCKS5 节点标记支持 UDP。显式代理探测 Google 和 Cloudflare 时，捕获到两条 UDP 连接，均为三段链、没有 DIRECT；每条观察到上传 20 字节，下载 0 字节。没有有效 STUN 回包。此数据说明代理管理器接受了探测，并不能证明最终上游接收或返回，更不能定位到某一家服务商。

新代码真实复测仍得到：系统路由无回包，显式本机 SOCKS 路径协商成功但三次探测无有效回包。App 的 UDP 详情分别显示这两层结果；只有实际收到并验证出口后才可能显示“代理 UDP 往返已验证”，不会把握手成功当成数据传输成功。

新增自建本机中继往返、拒绝外部中继、封装/分片/截断测试，全部 33 项 Rust 测试通过，格式/Clippy/前端语法通过；重新构建 App。不修改 Clash、代理选择、节点凭据或系统网络策略。

尚未实现的目标：当前真实代理链 UDP 正常往返、Claude/浏览器自动使用显式 SOCKS UDP、系统级防泄露拦截。若代理链本身不能提供 UDP 回包，仅靠 App 源码不能修复上游能力；需进一步排查链路或提供可往返的上游。协议依据：[RFC 1928](https://datatracker.ietf.org/doc/html/rfc1928)。
